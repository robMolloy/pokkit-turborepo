# Test Plan

## Scope

This plan covers **required tests for**:

- Collection bootstrap (`pb_config/collections.json` import vs create-and-write)
- First-user → approved `superadmin` provisioning (and no auto-elevation for later users)
- Global user permissions (`globalUserPermissions`), including the `superadmin` role and self-weaken hard rule
- Organisations (`organisations`) — create by global admin/superadmin, membership provisioning, and CRUD by org admin vs superadmin vs foreign global admin
- Organisation user permissions (`organisationUserPermissions`)
- Scope separation between global and organisation permissions
- Documented PocketBase API rule patterns for auth, global admin, global superadmin, org membership/admin, and org-admin-or-superadmin platform management

Tests describe what must be verified; they do not prescribe implementation details.

## Setup assumptions

- Stock PocketBase `users` auth collection is unchanged.
- On a ready instance, `globalUserPermissions`, `organisations`, and `organisationUserPermissions` exist with the fields and select values from the spec (see BOOT / schema tests for how they get there).
- `globalUserPermissions` has `userId`, `role` (`standard` | `admin` | `superadmin`), and `status` (`pending` | `approved` | `blocked`).
- The initial approved superadmin comes from first-user provisioning when the `users` collection was empty before that create (not from API self-elevation). Additional superadmins may still be seeded via install / migration / PocketBase admin when needed (e.g. recovery).
- `organisations` exists with at least `name` (and optional `description`).
- `organisationUserPermissions` exists with `userId`, `orgId`, `role` (`standard` | `admin`), `status` (`pending` | `approved` | `blocked`), and a unique `userOrgKey` per user/organisation pair.
- Consumer collections (or fixtures) use documented PocketBase API rules that query `@collection.globalUserPermissions` and/or `@collection.organisationUserPermissions`, including `status ?= "approved"` and admin-or-superadmin / superadmin-only / org-admin-or-superadmin patterns where applicable. Consumer fixtures do **not** imply superadmin god-mode unless the rule explicitly composes it.

## Collection bootstrap

### BOOT-01 — Missing `collections.json` creates permission collections

Checks that when `pb_config/collections.json` does **not** exist, the plugin creates `globalUserPermissions`, `organisations`, and `organisationUserPermissions` with the schema in the spec. Missing-file creation is a required success path, not an error.

### BOOT-02 — Missing `collections.json` writes the file

Checks that after programmatic creation (BOOT-01), the plugin writes the resulting collections out to `pb_config/collections.json` so subsequent starts can import them.

### BOOT-03 — Existing `collections.json` is imported

Checks that when `pb_config/collections.json` exists, the plugin imports collections from that file (including the three permission collections and their fields / rules as defined by the plugin), rather than treating absence of prior DB collections as a hard failure.

### BOOT-04 — Users collection unchanged

Checks that bootstrap does not alter the shape or behaviour of the default PocketBase `users` collection.

## First user → superadmin

### BOOT-05 — First user receives approved superadmin GUP

Checks that when the first `users` record is created (empty `users` collection before that create), the plugin creates a matching `globalUserPermissions` row for that user with `role = superadmin` and `status = approved`.

### BOOT-06 — Subsequent users are not auto-elevated

Checks that later `users` creates do **not** receive automatic `superadmin` (or any automatic elevation). Further GUP rows follow normal create / approval rules.

### BOOT-07 — Self-elevation to superadmin via GUP API denied

Checks that a non-superadmin cannot grant themselves `role = superadmin` through the normal `globalUserPermissions` API. After first-user provisioning, only another approved superadmin (or install / migration / PocketBase admin tooling) may grant `superadmin`.

---

## Schema and records — `globalUserPermissions`

### GUP-01 — Collection fields

Checks that `globalUserPermissions` exposes `userId` (relation → `users`), `role`, and `status` with the allowed select values from the spec.

### GUP-02 — Role values

Checks that only `standard`, `admin`, and `superadmin` are accepted for `role`, and invalid values are rejected.

### GUP-03 — Status values

Checks that only `pending`, `approved`, and `blocked` are accepted for `status`, and invalid values are rejected.

### GUP-04 — Relation to users

Checks that `userId` must point at a valid `users` record, and that deleting a user cascades (or otherwise cleans up) related global permission records as configured.

### GUP-05 — Assign roles with status lifecycle

Checks that a permission record can be created and updated through the status lifecycle (`pending` → `approved` → `blocked`) while keeping a `standard`, `admin`, or `superadmin` role (as applicable).

---

## Access to `globalUserPermissions` itself

### GUP-06 — Unauthenticated access denied

Checks that unauthenticated requests cannot list, view, create, update, or delete `globalUserPermissions` records.

### GUP-07 — Owner can read own record

Checks that an authenticated user can list/view their own `globalUserPermissions` record when rules allow self-access.

### GUP-08 — Non-superadmin cannot manage permissions

Checks that a user with an approved global `standard` or `admin` role (and any user who is not an approved superadmin) cannot create, update, or delete `globalUserPermissions` records for others, and cannot perform privileged self-changes that alter effective power.

### GUP-09 — Superadmin can manage others' permissions

Checks that an authenticated user with an approved global `superadmin` role can create, update, and delete other users' `globalUserPermissions` records — including elevating/demoting `role` (`standard` ↔ `admin` ↔ `superadmin`) and managing `status` (approve / block).

### GUP-10 — Superadmin can list/view others' permissions

Checks that an approved global superadmin can list and view permission records belonging to other users, and that an approved global admin alone cannot.

### GUP-11 — Superadmin cannot demote own role

Checks that an approved superadmin cannot update their own `role` away from `superadmin` (enforced reliably, e.g. before-update hook — not from API rules alone).

### GUP-12 — Superadmin cannot delete own record

Checks that an approved superadmin cannot delete their own `globalUserPermissions` record (e.g. before-delete hook).

### GUP-13 — Superadmin cannot weaken own status

Checks that an approved superadmin cannot set their own `status` to `blocked` or `pending`.

### GUP-14 — Superadmin can change another superadmin

Checks that an approved superadmin can demote, block, or delete a **different** superadmin's `globalUserPermissions` record. Demoting, blocking, or deleting a superadmin always requires a different approved superadmin.

### GUP-15 — Pending or blocked superadmin cannot manage GUP

Checks that a user whose global permission has `role = superadmin` but `status = pending` or `blocked` cannot manage `globalUserPermissions` for anyone.

### GUP-16 — Global admin cannot elevate roles

Checks that an approved global `admin` cannot elevate anyone to `admin` or `superadmin` (or otherwise create/update/delete others' GUP records).

## Rule-based access via global permissions

These tests assume another collection gates CRUD with the documented global-permission rule patterns (auth required; approved status; admin, admin-or-superadmin, or superadmin-only checks via `@collection.globalUserPermissions`).

### GUP-17 — Unauthenticated CRUD denied

Checks that requests without `@request.auth.id` are denied for list, view, create, update, and delete on a collection that requires authentication plus global permissions.

### GUP-18 — No permission record denied

Checks that an authenticated user with no `globalUserPermissions` row is denied access where rules require a matching global permission.

### GUP-19 — Approved global admin (or superadmin) allowed

Checks that a user with `role = admin` and `status = approved` is allowed through rules that require a global admin, and that an approved **superadmin** is also allowed when the documented pattern is admin **or** superadmin.

### GUP-20 — Superadmin-only rules deny global admin

Checks that rules requiring `role = superadmin` (plus approved status) allow an approved superadmin and **deny** an approved global admin.

### GUP-21 — Approved global standard role

Checks that a user with `role = standard` and `status = approved` is allowed only where rules require global standard (or any approved global member), and is **denied** where rules require `role = admin` or `role = superadmin`.

### GUP-22 — Pending status does not grant access

Checks that a user whose global permission has `status = pending` is denied by rules that require an approved permission, regardless of role (including `superadmin`).

### GUP-23 — Blocked status does not grant access

Checks that a user whose global permission has `status = blocked` is denied by rules that require an approved permission, regardless of role (including `superadmin`).

### GUP-24 — Admin or superadmin rule does not match wrong user

Checks that a global admin / superadmin rule only matches when `userId` equals the authenticated user; another user's admin or superadmin record must not grant the requester access.

### GUP-25 — CRUD actions covered independently

Checks that list, view, create, update, and delete each enforce the global permission rule attached to that action (a pass on one action does not imply a pass on another).

---

## Interaction with `users` (when rules reference global admins)

### GUP-26 — User can access own profile

Checks that a user can list/view their own `users` record under rules that allow `id = @request.auth.id`.

### GUP-27 — Global admin or superadmin can access other users

Checks that an approved global admin **or** approved superadmin can list/view other users' records when `users` rules allow access via the documented admin-or-superadmin pattern on `@collection.globalUserPermissions`.

### GUP-28 — Non-admin and non-superadmin cannot access other users

Checks that a user without an approved global admin or superadmin permission cannot list/view another user's record via that admin-or-superadmin branch of the rule.

---

## Organisations — schema

### ORG-01 — Collection fields

Checks that `organisations` exposes `name` (text) and `description` (text, optional) as defined in the spec.

---

## Organisations — create, provision, CRUD

### ORG-02 — Unauthenticated access denied

Checks that unauthenticated requests cannot list, view, create, update, or delete `organisations` records.

### ORG-03 — Approved global admin can create an organisation

Checks that an authenticated user with an approved global `admin` role can create an `organisations` record (documented org-create rule: approved global admin or superadmin).

### ORG-04 — Approved global superadmin can create an organisation

Checks that an authenticated user with an approved global `superadmin` role can create an `organisations` record.

### ORG-05 — Create provisions approved org-admin membership

Checks that creating an organisation provisions an `organisationUserPermissions` row for the creator with `role = admin`, `status = approved`, the correct `orgId`, and a unique `userOrgKey`. The same provisioning applies when a superadmin creates an org (consistent with the admin path).

### ORG-06 — Creator manages that organisation as org admin

Checks that the creator, as approved organisation admin, can update/delete that organisation and manage its `organisationUserPermissions` records. After create, that CRUD comes from org-admin membership, not from being a global admin.

### ORG-07 — Foreign global admin denied without membership

Checks that an approved global `admin` without membership in an organisation cannot list, view, update, or delete that organisation or its `organisationUserPermissions` merely because they are a global admin.

### ORG-08 — Later-granted org admin can manage that organisation

Checks that an approved organisation admin who was not the creator (later granted admin membership) can manage that organisation and its memberships. Access is membership-based, not "creator forever".

### ORG-09 — Superadmin can CRUD any organisation

Checks that an approved global `superadmin` can list, view, create, update, and delete any `organisations` record without membership in that organisation (org-admin-or-superadmin platform management pattern).

### ORG-10 — Superadmin can CRUD any organisationUserPermissions

Checks that an approved global `superadmin` can list, view, create, update, and delete any `organisationUserPermissions` record without membership in that organisation.

### ORG-11 — Approved global standard cannot create organisations

Checks that an approved global `standard` user cannot create an `organisations` record.

### ORG-12 — Pending or blocked global admin cannot create organisations

Checks that a global `admin` with `status = pending` or `blocked` cannot create an `organisations` record.

---

## Organisation user permissions — schema and records

### OUP-01 — Collection fields

Checks that `organisationUserPermissions` exposes `userId` (relation → `users`), `orgId` (relation → `organisations`), `role`, `status`, and `userOrgKey` with the allowed select values from the spec.

### OUP-02 — Role values

Checks that only `standard` and `admin` are accepted for `role`, and invalid values (including org-level `superadmin`) are rejected.

### OUP-03 — Status values

Checks that only `pending`, `approved`, and `blocked` are accepted for `status`, and invalid values are rejected.

### OUP-04 — Relation to users and organisations

Checks that `userId` must point at a valid `users` record and `orgId` must point at a valid `organisations` record.

### OUP-05 — Unique membership per user/organisation

Checks that `userOrgKey` enforces uniqueness so a user cannot have more than one membership record for the same organisation.

### OUP-06 — Assign roles with status lifecycle

Checks that a membership record can be created and updated through the status lifecycle (`pending` → `approved` → `blocked`) while keeping a `standard` or `admin` role for that organisation.

### OUP-07 — Multiple organisations for one user

Checks that the same user can hold separate `organisationUserPermissions` records for different organisations (different `userOrgKey` values).

---

## Access to `organisationUserPermissions` itself

### OUP-08 — Unauthenticated access denied

Checks that unauthenticated requests cannot list, view, create, update, or delete `organisationUserPermissions` records.

### OUP-09 — Member can read own membership

Checks that an authenticated user can list/view their own `organisationUserPermissions` record when rules allow self-access.

### OUP-10 — Non-admin cannot manage memberships

Checks that a user who is not an approved organisation admin for that org and not an approved global superadmin cannot create, update, or delete membership records for that organisation (including an approved global admin without membership).

### OUP-11 — Organisation admin can manage memberships in their org

Checks that an authenticated user with an approved organisation `admin` role can create, update, and delete `organisationUserPermissions` records for that organisation.

### OUP-12 — Organisation admin cannot manage other orgs

Checks that an organisation admin's manage access does not extend to membership records belonging to a different organisation.

### OUP-13 — Organisation admin can list/view members in their org

Checks that an approved organisation admin can list and view membership records for other users within the same organisation.

### OUP-14 — Superadmin can manage memberships in any org

Checks that an approved global `superadmin` can create, update, and delete `organisationUserPermissions` records for any organisation without holding membership in that organisation.

### OUP-15 — Global admin without membership cannot manage OUPs

Checks that an approved global `admin` without organisation membership cannot manage that organisation's `organisationUserPermissions` records.

## Rule-based access via organisation permissions

These tests assume another collection stores (or otherwise references) an organisation id and gates CRUD with the documented organisation-permission rule patterns (auth required; membership / admin checks via `@collection.organisationUserPermissions` matching `userId`, `orgId`, `status`, and optionally `role`). Unless noted, fixtures use **pure OUP** rules without a composed superadmin bypass.

### OUP-16 — Unauthenticated CRUD denied

Checks that requests without `@request.auth.id` are denied for list, view, create, update, and delete on a collection that requires authentication plus organisation permissions.

### OUP-17 — No membership record denied

Checks that an authenticated user with no `organisationUserPermissions` row for the record's organisation is denied access where rules require matching membership.

### OUP-18 — Approved organisation admin allowed

Checks that a user with `role = admin`, `status = approved`, and `orgId` matching the record's organisation is allowed through rules that require an organisation admin.

### OUP-19 — Approved organisation standard role

Checks that a user with `role = standard` and `status = approved` for the record's organisation is allowed only where rules require organisation membership / standard access, and is **denied** where rules require `role = admin`.

### OUP-20 — Pending status does not grant access

Checks that a membership with `status = pending` is denied by rules that require an approved permission, regardless of role or matching `orgId`.

### OUP-21 — Blocked status does not grant access

Checks that a membership with `status = blocked` is denied by rules that require an approved permission, regardless of role or matching `orgId`.

### OUP-22 — Membership does not cross organisations

Checks that an approved membership (standard or admin) for organisation A does not grant access to records belonging to organisation B.

### OUP-23 — Admin rule does not match wrong user

Checks that an organisation admin rule only matches when `userId` equals the authenticated user; another member's admin record for the same organisation must not grant the requester access.

### OUP-24 — Org rule does not match wrong organisation id on the record

Checks that rules comparing `organisationUserPermissions.orgId` to the record's organisation field deny access when those ids differ, even if the user is an approved admin of some other organisation.

### OUP-25 — CRUD actions covered independently

Checks that list, view, create, update, and delete each enforce the organisation permission rule attached to that action (a pass on one action does not imply a pass on another).

---

## Global vs organisation scope separation

### OUP-26 — Global admin is not implied by organisation admin

Checks that an approved organisation admin without a matching `globalUserPermissions` admin (or superadmin) record is denied where rules require a **global** admin or superadmin. Organisation admin ≠ global admin ≠ superadmin.

### OUP-27 — Global permission is not implied by organisation membership

Checks that an approved organisation membership (standard or admin) alone does not satisfy rules that only query `globalUserPermissions`.

### OUP-28 — Organisation rule is not satisfied by global admin or standard alone

Checks that an approved global admin or standard without membership in the record's organisation is denied where consumer rules require `@collection.organisationUserPermissions` for that organisation—unless a composed rule explicitly also allows global access.

### OUP-29 — Organisation rule is not satisfied by superadmin alone on pure OUP consumer rules

Checks that an approved global superadmin without membership in the record's organisation is denied on consumer collections that use pure OUP rules (no composed superadmin bypass). Superadmin bypass on arbitrary consumer data is optional and must be an explicit composed rule.

### OUP-30 — Platform org/OUP rules allow superadmin without membership

Checks that on `organisations` and `organisationUserPermissions`, an approved global superadmin satisfies the org-admin-or-superadmin platform management pattern without holding organisation membership.

### OUP-31 — Superadmin-only checks deny global admin

Checks that rules requiring `role = superadmin` deny an approved global `admin`.

### OUP-32 — Superadmin is not implied by organisation admin

Checks that an approved organisation admin without a matching `globalUserPermissions` superadmin record is denied where rules require a **global** superadmin.

### OUP-33 — Tenant control comes from membership, not global admin role alone

Checks that after organisation create, the creator's CRUD on that organisation and its memberships is granted through approved org-admin membership, and that removing or lacking that membership leaves an otherwise approved global admin without tenant control of that org.
